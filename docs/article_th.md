# FlowState — สถานะภายนอกสำหรับ workflow ที่ไม่มีสถานะ
สถานะนั้น:
  - ถูกสร้างอย่างชัดเจน
  - ถูกแก้ไขอย่างชัดเจน
  - ถูกอ่านอย่างชัดเจน
  - ถูกทำลายอย่างชัดเจน
สิ่งนี้ทำให้การเปลี่ยนแปลงสถานะสามารถมองเห็นได้ ตรวจสอบได้ และง่ายต่อการคิดวิเคราะห์
### สถานะเป็นอินพุต/เอาต์พุตอันดับหนึ่ง
ใน workflow ที่ใช้ FlowState:
  - สถานะไม่ถูกฝังอยู่ภายในรายการ
  - สถานะไม่ถูกส่งผ่านโหนดอย่างแฝง
  - สถานะไม่ถูกสร้างขึ้นใหม่ผ่านการรวม
แต่สถานะกลายเป็น:
  - อินพุตของขั้นตอน
  - เอาต์พุตของขั้นตอน
สิ่งนี้สะท้อนวิธีที่วิศวกรคิดเกี่ยวกับกระบวนการหลายขั้นตอน — แต่โดยไม่บังคับให้เครื่องมือจัดการ workflow จำลองหน่วยความจำ
### เครื่องมือจัดการ workflow ยังคงไม่มีสถานะ
FlowState ไม่ต่อสู้กับการออกแบบของเครื่องมืออย่าง n8n
มันยอมรับมัน
เครื่องมือจัดการ workflow ยังคง:
  - สามารถเริ่มต้นใหม่ได้
  - สามารถดำเนินการแบบขนานได้
  - ทำนายได้
ทุกการเปลี่ยนแปลงถูกผลักไปยังขอบเขต ซึ่งเป็นที่ที่มันควรอยู่
### ทำไมสิ่งนี้จึงเหมาะกับ LLMs โดยเฉพาะ
workflow ที่ขับเคลื่อนด้วย LLMs ขยายจุดอ่อนของการดำเนินการแบบไม่มีสถานะ:
  - การสร้างข้อความทีละขั้นตอน
  - การลองอีกครั้ง
  - ความล้มเหลวบางส่วน
  - ห่วงโซ่ที่ดำเนินการเป็นเวลานาน
  - การสะสมบริบท
โดยการนำสถานะไปภายนอก:
  - แต่ละการเรียกใช้ LLM สามารถเพิ่มหรือแก้ไขได้อย่างปลอดภัย
  - การลองอีกครั้งไม่ทำให้เนื้อหาซ้ำ
  - ความคืบหน้าบางส่วนถูกเก็บไว้
  - ผลลัพธ์ยาวๆ ถูกสร้างขึ้นทีละขั้นตอน
FlowState ไม่พยายามเป็นอัจฉริยะเกี่ยวกับเนื้อหา
มันเพียงรับประกันการเปลี่ยนแปลงสถานะที่แน่นอน
 
### แนวคิดเล็กๆ ที่มีจุดประสงค์
การออกแบบที่สำคัญที่สุดใน FlowState คือสิ่งที่มันไม่ทำ
มันไม่:
  - อนุมานเจตนา
  - รวมโครงสร้างอัตโนมัติ
  - ซ่อนความขัดแย้ง
  - จัดการ workflow
  - เก็บข้อมูลตลอดไป
ด้วยการอยู่เล็ก FlowState กลายเป็น:
  - ง่ายต่อการไว้วางใจ
  - ง่ายต่อการตรวจสอบ
  - ง่ายต่อการแทนที่
ข้อจำกัดนี้คือคุณสมบัติ
  - การออกแบบที่ไม่เปลี่ยนแปลง
  - โมเดลสถานะ
  - API HTTP
  - การจัดการความขัดแย้ง (เริ่มต้นใหม่ / แทนที่)
## ตัวอย่างที่ชัดเจนกับ n8n
เพื่อทำให้แนวคิดเป็นรูปธรรม ลองดูที่ workflow ที่ง่ายแต่มักพบในชีวิตจริง:
#### การสร้างบทความยาวๆ ทีละขั้นตอนโดยใช้ LLM
### วิธีทั่วไปของ n8n
โดยไม่มีสถานะภายนอก workflow ประเภทนี้มักจะมี:
  - โหนดวนเพื่อวนรายการส่วน
  - โหนดรวมเพื่อรวมผลลัพธ์ย่อย
  - การจัดการรายการเพื่อรักษาลำดับ
  - ตรรกะป้องกันเพื่อหลีกเลี่ยงการซ้ำเมื่อลองอีกครั้ง
แต่ละการเรียกใช้ LLM สร้างส่วนย่อย แต่ n8n ไม่มีที่เก็บส่วนย่อยเหล่านั้นโดยธรรมชาติ
สถานะต้องถูกจำลองผ่านรายการ
สิ่งนี้ทำงานได้ — จนกระทั่งมันไม่ได้
การลองอีกครั้งทำให้เนื้อหาซ้ำ
ความล้มเหลวบางส่วนทำให้ความคืบหน้าถูกรีเซ็ต
กราฟ workflow เติบโตซับซ้อนมากกว่าตรรกะทางธุรกิจ
### workflow เดียวกันกับ FlowState
ด้วย FlowState workflow กลายเป็นเส้นตรง
#### ขั้นตอนที่ 1 — สร้างสถานะการดำเนินการ
ในจุดเริ่มต้นของ workflow n8n สร้างสถานะ:
```json
POST /state
{
  "context": {
    "engine": "n8n",
    "executionId": "{{ $execution.id }}",
    "workflowId": "{{ $workflow.id }}",
    "topic": "AI consciousness",
    "language": "en"
  },
  "onConflict": "resume"
}
```

#### FlowState คืนค่า runId
runId นี้ถูกเก็บไว้หนึ่งครั้งและถูกใช้ตลอด workflow
หาก workflow ถูกลองอีกครั้งด้วยบริบทการดำเนินการเดียวกัน FlowState จะเริ่มต้นสถานะที่มีอยู่แทนที่จะสร้างสถานะใหม่

ขั้นตอนที่ 2 — สร้างส่วน
แต่ละโหนด LLM รับผิดชอบหน่วยงานหนึ่ง
มัน:
1 อ่านสถานะปัจจุบัน
2 สร้างส่วนใหม่
3 เพิ่มมันอย่างชัดเจน

```json
POST /state/{runId}/append
{
  "path": "sections",
  "value": {
    "type": "markdown",
    "content": "# Introduction\nAI is evolving rapidly...",
    "createdAt": 1700000012345
  }
}
```
ไม่มีโหนดรวม
ไม่มีการวนซ้ำที่จัดการการสะสม
เพียงแค่การเพิ่มที่ชัดเจนเดียว

ขั้นตอนที่ 3 — ลองอีกครั้งโดยไม่ต้องกลัว
หากการเรียกใช้ LLM หมดเวลาหรือ workflow ถูกลองอีกครั้ง:
ส่วนที่มีอยู่ยังคงไม่เปลี่ยนแปลง

ส่วนใหม่ถูกเพิ่มเพียงครั้งเดียว

ลำดับถูกเก็บไว้

สถานะอยู่ภายนอกกราฟการดำเนินการ

ขั้นตอนที่ 4 — การสิ้นสุด
ที่จุดสิ้นสุดของ workflow โหนดสุดท้ายอาจ:
รวม markdown ทั้งหมด

สร้าง HTML

เผยแพร่เนื้อหา

เขียนสรุป

```json
PATCH /state/{runId}
{
  "output": {
    "markdown": "{{ assembled_markdown }}",
    "publishedUrl": "https://example.com/article"
  },
  "meta": {
    "status": "success"
  }
}
```
### สิ่งที่เปลี่ยนไป?
กราฟ workflow กลายเป็น:
  - สั้นลง
  - ง่ายต่อการอ่าน
  - ง่ายต่อการตรวจสอบ
ความซับซ้อนถูกย้ายไปยังที่ที่มันควรอยู่:
#### คือการเปลี่ยนแปลงสถานะที่ชัดเจน ไม่ใช่การเล่นกับตรรกะการควบคุม
FlowState ไม่ทำให้ n8n "มีสถานะ"
มันเพียงให้สถานะมีสถานที่อยู่
### ทำไมสิ่งนี้จึงขยายได้ดีกว่า
รูปแบบนี้ขยายได้อย่างเป็นธรรมชาติไปยัง:
  - workflow วิจัยหลายขั้นตอน
  - ท่อระบายน้ำ LLM แบบเอเจนต์
  - การดำเนินการที่ใช้เวลานาน
  - การเริ่มต้นใหม่บางส่วน
  - สาขาขนานที่เขียนไปยังการดำเนินการเดียวกัน
ตราบใดที่ทุกขั้นตอนตกลงกันเกี่ยวกับ runId พวกมันจะแบ่งปันแหล่งความจริงเดียวกัน
## ข้อจำกัดและข้อแลกเปลี่ยน
FlowState ถูกจำกัดอย่างมีเจตนา
มันแก้ปัญหาเฉพาะเจาะจง:
#### การแบ่งปันสถานะที่เปลี่ยนแปลงได้ระหว่างขั้นตอนของ workflow เดียวกัน
ทุกสิ่งที่อยู่นอกเหนือขอบเขตนี้ถูกมองว่าไม่สนับสนุนหรือถูกหลีกเลี่ยงโดยเจตนา
### ไม่มีการรับประกันความทนทาน
FlowState เป็นบริการในหน่วยความจำ
หากกระบวนการรีสตาร์ท สถานะจะหายไป
นี่ไม่ใช่ข้อบกพร่อง — นี่คือข้อแลกเปลี่ยน
FlowState ถูกออกแบบมาสำหรับ:
  - การดำเนินการที่มีชีวิตสั้นถึงกลาง
  - workflow ที่สามารถลองอีกครั้งหรือเริ่มต้นใหม่ได้
  - สถานะที่สามารถคำนวณใหม่ได้หากจำเป็น
หากคุณต้องการความทนทานที่แข็งแกร่ง การจัดการเวอร์ชัน หรือการเล่นย้อนหลัง FlowState ไม่ใช่เครื่องมือที่เหมาะสม
### ไม่มีการประสานงานระดับโลก
สถานะมีขอบเขตการดำเนินการ
FlowState ไม่:
  - ประสานงานระหว่างการดำเนินการ
  - สื่อสารระหว่าง workflow หลายตัว
  - ให้การล็อกหรือการทำธุรกรรมข้ามการดำเนินการ
สิ่งนี้รักษาโมเดลให้เรียบง่ายและหลีกเลี่ยงการเปลี่ยน FlowState ให้เป็นระบบกระจาย
### ไม่มีการควบคุมการเขียนที่ใช้ร่วมกัน
FlowState ไม่พยายามแก้ปัญหาการเขียนที่ใช้ร่วมกันในระดับทั่วไป
ความขัดแย้งถูกจัดการในช่วงการสร้างการดำเนินการ (onConflict: resume | replace) ไม่ใช่ในระดับฟิลด์หรือการดำเนินการ
นี่เพียงพอสำหรับ:
  - workflow ที่แน่นอน
  - กราฟการดำเนินการที่ควบคุมได้
  - การเปลี่ยนแปลงที่สามารถทำซ้ำได้
มันไม่เหมาะกับสถานะที่ใช้ร่วมกันที่มีความแข่งขันสูง
### ไม่มีภาษาค้นหา
FlowState เปิดเผย API HTTP ขนาดเล็ก
คุณสามารถ:
  - อ่านสถานะทั้งหมด
  - เปลี่ยนแปลงเส้นทางที่รู้จัก
  - เพิ่มข้อมูลที่มีโครงสร้าง
คุณไม่สามารถ:
  - รันคำสั่งค้นหาที่ซับซ้อน
  - กรองข้อมูลย้อนหลัง
  - รวมข้อมูลจากหลายการดำเนินการ
นี่คือการเลือกที่ตั้งใจเพื่อรักษาพื้นที่ผิวให้เล็ก
### การจัดการวงจรชีวิตที่ชัดเจน
สถานะหมดอายุผ่าน TTL
ไม่มี:
  - การเก็บรักษา
  - การสำรองข้อมูล
  - กลไกฟื้นฟู
เมื่อหมดอายุ การดำเนินการก็หายไป
สิ่งนี้บังคับให้ workflow:
  - เสร็จสิ้นหรือล้มเหลวอย่างชัดเจน
  - รับสถานะเป็นข้อมูลชั่วคราว
  - หลีกเลี่ยงการสะสมที่เงียบ
### สรุปข้อแลกเปลี่ยน
โดยยอมรับข้อจำกัดเหล่านี้ FlowState ยังคงเป็น:
  - เล็ก
  - สามารถเข้าใจได้
  - ตรวจสอบได้
  - ง่ายต่อการใช้ผิด
  - ง่ายต่อการแทนที่
FlowState ไม่ได้ถูกออกแบบมาเพื่อเป็นโครงสร้างพื้นฐานหลัก
มันคือเครื่องมือสนับสนุน — สิ่งที่คุณสามารถพึ่งพาได้โดยไม่ต้องสร้างระบบของคุณรอบมัน
## ทำไมผมจึงแบ่งปันสิ่งนี้
FlowState เริ่มต้นจากเป็นการแก้ปัญหาส่วนตัว
ผมไม่ได้พยายามสร้างผลิตภัณฑ์ บริษัท หรือแพลตฟอร์มใหม่
ผมพยายามกำจัดอุปสรรคจาก workflow ของตัวเอง
ขณะที่สร้าง automation ที่ซับซ้อน — โดยเฉพาะที่เกี่ยวข้องกับ LLMs และการสร้างเนื้อหาหลายขั้นตอน — ผมพบกับปัญหาเดียวกันเสมอ:
เครื่องมือที่ไม่มีสถานะมีความเรียบง่าย แต่พวกมันผลักความซับซ้อนโดยไม่ตั้งใจไปยัง workflow ตัวเอง
แทนที่จะแสดงสิ่งที่ควรเกิดขึ้น ผมใช้เวลากับการต่อสู้กับวิธีที่สถานะถูกส่งผ่านโหนด การวนซ้ำ และการรวม
ดังนั้น ผมจึงสร้างสิ่งเล็กที่สุดที่สามารถแก้ปัญหานี้ได้
สิ่งที่ทำให้ผมประหลาดใจไม่ใช่ความจริงที่ว่ามันทำงานได้ —
มันคือความถี่ที่ผมใช้มันเมื่อมันมีอยู่
### สิ่งที่ผมเรียนรู้
ระบบแบบไม่มีสถานะมีความยอดเยี่ยม — จนกระทั่งคุณต้องการความเปลี่ยนแปลงที่ควบคุมได้และมีขอบเขต
การนำสถานะภายนอกสามารถทำให้ workflow ง่ายขึ้นแทนที่จะซับซ้อน
ข้อจำกัดที่เข้มงงไม่ใช่ข้อจำกัด; นี่คือสิ่งที่ทำให้เครื่องมือใช้งานได้
บริการเล็กๆ ที่มีขอบเขตชัดเจนมีอายุยืนยาวกว่า "นามธรรมที่ยืดหยุ่น"
สำคัญที่สุด:
คุณไม่ต้องการแพลตฟอร์มที่ใหญ่ขึ้นเสมอไป — บางครั้งคุณต้องการเครื่องมือที่คมคัตมากกว่า
### ทำไมสิ่งนี้จึงอาจช่วยผู้อื่น
หากคุณเป็น:
  - ผู้ใช้ n8n, Temporal, หรือเครื่องมือจัดการที่ไม่มีสถานะอื่นๆ
  - สร้าง workflow ที่ใช้ LLM มากหรือแบบวนซ้ำ
  - หมดความอดทนกับการวนซ้ำที่เปราะบาง การรวม และการจัดการรายการ
  - มองหาสิ่งที่เบาบางที่คุณสามารถใช้เองได้
FlowState อาจช่วยคุณประหยัดเวลาได้ — หรืออย่างน้อยก็ให้คุณมีมุมมองใหม่เกี่ยวกับสถานะ
และหากคุณไม่ได้ใช้มันจริงๆ ผมยังหวังว่าแนวทางการออกแบบนี้จะมีประโยชน์
## ขั้นต่อไป (อาจ)
FlowState มีขนาดเล็กโดยเจตนา และผมต้องการรักษาขนาดนั้นไว้
อย่างไรก็ตาม ทิศทางบางอย่างดูเหมือนมีคุณค่าที่จะสำรวจ — อย่างระมัดระวัง:
  - การรับรอง / การควบคุมการเข้าถึง ถ้ามันจำเป็นต้องเปิดใช้งานนอกเครือข่ายส่วนตัว
  - ความมองเห็นที่ดีขึ้น โดยส่วนใหญ่สำหรับการตรวจสอบและตรวจสอบ
  - การเก็บข้อมูลที่เลือกได้ ตามที่ต้องการ สำหรับกรณีการใช้งานเฉพาะ
  - การกำหนดประเภทที่เข้มงงและตรวจสอบความถูกต้อง เพื่อทำให้การใช้ผิดง่ายขึ้น
ไม่มีอะไรเป็นสัญญา
คุณค่าของ FlowState มาจากข้อจำกัด
การพัฒนาใดๆ ต้องรักษาสิ่งนี้ไว้ — หรือมันอาจไม่คุ้มค่าที่จะทำ
หาก FlowState หยุดเป็นเครื่องมือที่มีประโยชน์ มันควรจะง่ายต่อการแทนที่
นี่ไม่ใช่ความล้มเหลว — นี่คือการออกแบบที่ทำงานตามเจตนา
